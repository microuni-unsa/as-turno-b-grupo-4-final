# AGENTS.md — Engineering Rules & Constraints

## 1. Testing and Mocking Rules
- **Enforce Vitest Primitives**: Always use standard `vi.mock()` and `vi.spyOn()` from Vitest when mocking module boundaries, network calls, or clock timers in unit tests.
- **No Mock Provider Implementations**: Never, under any circumstance, implement custom mock provider classes (e.g., do NOT create `MockModelProvider`, `FakePimsAdapter`, or handwritten dummy provider stubs). All provider abstractions must point to actual implementations or have their calls intercepted cleanly via `vi.mock` / `vi.spyOn`.
- **Zero-Cost Model Testing**: Tests must never call live LLM/embeddings APIs over the network. Always intercept `ModelProvider` methods (`embed`, `chat_json`, `rerank`) using Vitest `vi.spyOn()` on the concrete `OpenAIModelProvider` instance to eliminate token costs while running authentic pgvector and retrieval pipelines.
- **Integration Tests with Real Data Store**: For PIMS integration tests, we run our reverse-engineered PIMS API server (built with Hono and Drizzle ORM) backed by a real PostgreSQL data store in testcontainers. The schema and initial data are mounted into `/docker-entrypoint-initdb.d/` (`01-gestitel.sql` and `02-seed.sql`) and run natively on container boot.
- **Strict Prohibition of Static or Mocked Runtime Data**: In runtime execution, all data must be 100% authentic, live, and substantive. No canned strings, hardcoded incident payloads, placeholder text, or generic hand-waving (e.g., no saying "clauses xxx and yyy apply"). Dual-Modal RAG must extract and display exact verbatim quotes, chunk identifiers, and similarity scores. Root-cause analyses, containment actions, and audit findings must reflect live PIMS records and dynamic LLM inferences.

## 2. Secrets, Tooling & Configuration
- **Secrets Management**: Production secrets are managed via environment variables and deterministic `*_CMD` secret-fetching commands per spec §11.2; no plaintext production API keys, passwords, or tokens in git. A local gitignored `.env` (never committed; template in `.env.example`) holds local configurations and credentials.
- **Tooling & Nix Policy**: NEVER assume Nix is available dynamically at runtime. If system packages or CLI tools are needed, declare them explicitly in `flake.nix`. All JavaScript/TypeScript dependencies must be managed via `bun` in `package.json`. The Presidio PII-redaction sidecar image + `es_core_news_md` model pins live in `flake.nix`/compose per spec §11.3/`PRESIDIO_*`.
- **PII Redaction (formal libs only)**: Pre-LLM redaction is performed by the pinned Presidio analyzer sidecar (`language: "es"`, custom `PE_DNI`/`PE_RUC` recognizers); `libphonenumber-js`/`tldts`/`zod` remain only as post-redaction validators in the `AgentModelClient` gate. App-level regex MUST NOT be a PII detection path. Sidecar failure → `PII_REDACTION_UNAVAILABLE` fail-closed (never unredacted send, never regex fallback). Golden redaction fixtures (spec A24) re-run on any image/model bump.
- **LLM Provider**: Configurable model provider abstraction implemented via `OpenAIModelProvider` (OpenAI SDK / OpenAI-compatible cloud endpoint, e.g. Mistral API via OpenAI client compatibility). Environment credentials manage API keys deterministically. Keep token usage strictly bounded and cheap.
- **Continuous Daemon & Docker Deployment**: The system runs continuously as an autonomous background daemon configured via environment variables (`bun run start`). `AUTO_NOTIFY=false` (default) parks approved notice packs at `AWAITING_APPROVAL` until a human `change_incident` approval; `AUTO_NOTIFY=true` sends automatically and only then applies `HUMAN_VETO_WINDOW_MIN`. Guided-create submit (`channel: "cockpit_guided"`) during `OPERATOR_HALT` is rejected (halt freezes capture); draft/explain stay available. A production build target (`bun run build`) compiles a standalone distribution runnable inside a minimal `Dockerfile` + `docker-compose.yml`. No presentation runbooks or staged demonstration scripts are permitted.

## 3. Architecture & Code Quality
- **Monorepo Structure**: The repository is organized as a Bun workspace monorepo under `packages/`:
  - `@pims/types`: Strict Zod schemas, inferred TypeScript types, and central error taxonomy.
  - `@pims/config`: Centralized configuration manager with fail-fast validation. PIMS auth mode is password (`PIMS_USERNAME` + `PIMS_PASSWORD`, plain env value); daemon settings include `EVIDENCE_DB_URL`, `RAG_CORPUS_DIR`, `AUTO_NOTIFY`, and `WATCHER_POLL_INTERVAL_MS`.
  - `@pims/models`: Configurable `ModelProvider` abstraction (`OpenAIModelProvider`).
  - `@pims/rag`: Ingestion, Dual-Modal Index (Pgvector + MiniSearch BM25) with Reciprocal Rank Fusion (RRF), and cross-encoder rerank retrieval pipeline producing exact verbatim normative quotes.
  - `@pims/pims-mock`: Reverse-engineered PIMS test API server using Hono and Drizzle ORM.
  - `@pims/pims-adapter`: Production PIMS HTTP client adapter (endpoints E01–E26).
  - `@pims/evidence`: Local PostgreSQL + Drizzle ORM evidence store, AES-256-GCM encryption at rest, blob staging with root-confined storage paths, forensic hash integrity verification, and canonical-JSON bundle sealer.
  - `@pims/notices`: GDPR Art 33 authority pack composer, Art 34 subject notice composer, `Intl.Segmenter` plain-language validator with per-token numeric approvals, and Art 34(3) statutory exemption engine driven by structured reviewer attestations (`EncryptionProofAttestation`, `SubsequentMeasure`, `DisproportionateEffort`).
  - `@pims/agent`: the agent brain on top of phases 1–3 — 8 role definitions with versioned prompt hashes and allow/deny tool matrices (`orchestrator/roles.ts`), the 19-tool registry with strict Zod argument/result validation, role patch policies and the `tool_ledger` audit trail (`tools/`), the fixed-order lifecycle state machine and autonomous orchestrator (`orchestrator/lifecycle.ts`, `orchestrator/orchestrator.ts`), countdown deadline scheduler (`orchestrator/scheduler.ts`), single-prompt root-cause analysis (`orchestrator/orchestrator.ts`), notice drafting (`review/draft-service.ts`), single-pass notice challenge reviewer with deterministic legal-completeness, citation, plain-language, PII, and close-checklist checks (`review/reviewer.ts`), lifecycle helpers for evidence markers, the 8-item close checklist and dedupe (`lifecycle/`), the indicator emitter (`indicators/`), the PII-gated model client (`llm/safe-prompt.ts`), and the autonomous live incident watcher daemon (`orchestrator/watcher.ts`).
  - `@pims/cockpit`: Glass-Box Cockpit — JSON/SSE backend plus the Astro + Starwind UI + Lucide-icon web UI it serves (product record in `packages/cockpit/PRODUCT.md`; UI visually follows the GESTITEL PIMS SPA, cleaned up). Dictation input is browser Web Speech API only (no backend STT). Authenticates against live PIMS E01/E04, maps native roles (`Administrador`, `Operador`, `Editor`, `Lector`) and the E01 permission matrix, streams agent events (`role:transition`, `rag:retrieval`, `tool:mutation`, `review:approval_requested`, `lifecycle:status_change`, timer ticks) over `/api/stream`, and exposes guided-create (draft/explain/submit per spec §8.4), approve/revision/Art 34(3)(a) exemption/chat endpoints plus `/healthz` and `/readyz`. Guided-create helpers follow the chat-tools pattern (direct async helpers + single redacted `chat_json` calls, not §5 manifest tools); chat citations are grounded in stored retrieval records and validated by `chunk_sha256` + retriever scores; PII never enters model prompts (Presidio sidecar, spec §11.3).
- **Path Imports**: Follow `biome.json` strictly: relative imports (`./` or `../`) are forbidden. Always use `@pims/*` package imports.
- **Type Rigor & Zod Validation**: Loose types (such as `(string & {})`, `unknown`, `any`, and arbitrary `Record<string, unknown>`) are strictly forbidden in public contracts. Every domain model and API request/response shape must have a dedicated Zod schema and inferred TypeScript type.
- **Exhaustive Branching & Explicit State**: Every `if/else`, `switch`, or pattern match must explicitly manage state or raise a defined error. No silent `pass`, empty blocks, or warning-only logging.
- **Zero Fallbacks & Deterministic Control Flow**:
  - No machine-dependent path fallbacks (e.g., hardcoded absolute paths, `fs.existsSync(p1) ? p1 : p2`). Paths must resolve deterministically relative to workspace/project root or fail fast.
  - No speculative fallback cascades (e.g., catching errors and falling back through multiple speculative auth methods). If an expected token or credentials fail, fail fast with spec-defined named errors.
- **No Repeated Cross-File Literals**: Centralize constants, enums, error codes, and configuration parameters in `@pims/types` or designated config modules.

## 4. Specification & Agent Documentation Synchronization
- **Spec Modification Policy**: The project specifications (`docs/incident-agent-spec.md` and phase documentation) can be modified with explicit user consent.
- **Automatic Synchronization**: `AGENTS.md` and the specification files must always be kept up to date automatically whenever architectural decisions, contract shapes, or engineering constraints change.
